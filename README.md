# umir-frontend

React-приложение для оператора одного ресторана. Vite собирает статические файлы, а Nginx раздаёт их и передаёт `/api/` в gateway.

## Стек

| Область            | Выбор                                                 | Состояние                                                                                |
| ------------------ | ----------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Язык и интерфейс   | TypeScript, React, Vite                               | Используются для публичной части.                                                        |
| Маршрутизация      | react-router                                          | `createBrowserRouter`; маршруты перечислены в «Текущем состоянии».                       |
| Компоненты и стили | Chakra UI с Emotion                                   | Собственная тема из Figma; стандартные токены и recipes Chakra не подключены.            |
| SCSS               | Sass                                                  | Установлен, но не используется: стили описаны токенами и recipes темы Chakra.            |
| Шрифты             | IBM Plex Sans и IBM Plex Mono через `@fontsource`     | Раздаются вместе со сборкой, без сторонних CDN.                                          |
| Проверки           | ESLint, dependency-cruiser, Prettier, TypeScript, Bun | Проверки выполняются командами из раздела «Разработка».                                  |
| Сборка и раздача   | Node.js, Vite, Nginx                                  | Существующий контейнерный процесс сохранён; Docker-сборка копирует `public/` с иконками. |

Презентация организаторов рекомендует JavaScript или TypeScript, React, SCSS и Chakra UI. Выбраны TypeScript и Chakra UI. SCSS не понадобился, потому что цвета, отступы, типографика, радиусы, анимации и точки перелома хранятся в одной теме Chakra. Версии React и Vite не менялись.

Тема собрана через `createSystem(defaultBaseConfig, …)` в `src/presentation/theme`. В ней только токены из [макета UmirHack](https://www.figma.com/design/6Y1Jglyvc1xVsTzII54A2u/UmirHack); CSS-переменные имеют префикс `--umir-`. Размеры задаются в `rem`. Точки перелома mobile-first: `sm` 768px, `md` 881px, `lg` 1025px, `xl` 1201px, `2xl` 1367px, `3xl` 2400px. Макеты 390, 1024 и 1440 соответствуют базовым стилям, `sm`–`lg` и `xl`. Новые цвета и отступы добавляйте в тему, а не значениями в компонентах.

В `tsconfig.json` включён `skipLibCheck`. Без него TypeScript находит 17 ошибок в типах Ark UI, Chakra UI и zag-js, которые несовместимы с `exactOptionalPropertyTypes`. Код в `src` проверяется полностью.

## Архитектура

Исходники разделены на пять слоёв. Зависимости направлены к бизнес-правилам интерфейса; сборка приложения соединяет слои.

| Слой               | Ответственность                                                    | Может зависеть от                       |
| ------------------ | ------------------------------------------------------------------ | --------------------------------------- |
| `src/domain`       | Независимые от фреймворка значения и состояния интерфейса.         | `domain`                                |
| `src/application`  | Сценарии интерфейса и порты, определённые их потребителями.        | `application`, `domain`                 |
| `src/adapters`     | HTTP, хранилища, runtime-декодирование и другие внешние механизмы. | `adapters`, `application`, `domain`     |
| `src/presentation` | React-представление, тема Chakra и статические ассеты.             | `presentation`, `application`, `domain` |
| `src/app`          | Точка входа и сборка приложения.                                   | Все слои                                |

Только `adapters`, `presentation` и `app` могут импортировать сторонние runtime-пакеты. Представление не создаёт HTTP-адаптеры. В пустые слои не добавляют фиктивную бизнес-логику. Production-код в `src` использует только `.ts` и `.tsx`; ESLint отклоняет JavaScript. Dependency-cruiser проверяет допустимые зависимости, включая type-only импорты и алиас `@/`, циклы, неразрешённые и нераспознанные импорты и импорты тестовых данных в production-код. ESLint запрещает inline disable, прямые `fetch` и storage-вызовы из presentation, а также неинъецируемые часы, ID и внешние механизмы в domain/application.

Сейчас слои заполнены так:

- `domain`:
  - `feedback.ts` — черновик формы обратной связи и проверка формата полей по [контракту feedback](https://github.com/JustIkra/umir-feedback/issues/1);
  - `access.ts` — роли и права backend v2 в одном ресторане и право, которое нужно разделу; права разных ресторанов не складываются;
  - `ids.ts` — проверка идентификаторов: канонический UUIDv4 в нижнем регистре.
- `application`:
  - `api` — общие типы контракта: исходы `committed`, `not_committed`, `unknown`, `unavailable`, `indeterminate`, контекст бизнес-чтения с runtime-эпохой и `stateVersion`, отказ `ApiError` с кодом, исходом и `retryable`;
  - `account` — порт `AccountApi`: `GET /api/v2/me`, вход паролем с `commandID` и выход; пользователь, сроки сессии и CSRF-токен;
  - `access` — порт `AccessApi` для `GET /api/v2/access`, хранилище доступа с состояниями `loading`, `ready` и `unverified`, права по каждому ресторану и выбор ресторана для `/app`; порт `LastRestaurantStore`;
  - `epochs` — runtime-эпохи warehouse и serving по ресторанам; новая эпоха означает перезапуск сервиса;
  - `commands` — попытки команд: одна на ключ, с `commandID` и эпохой своего сервиса. Неизвестный исход сохраняет попытку, а повтор отправляет её же с тем же `commandID`. `RuntimeReset` и исход `indeterminate` означают, что исход потерян, а данные ресторана устарели;
  - `models` — реестр моделей чтения по ресторану и темам потока; записывает эпоху каждого бизнес-чтения и при её смене показывает «Данные обновились»;
  - `failure` — состояние экрана по отказу чтения: сессия закончилась, нет прав, ресторан удалён, сервис не готов, лимит запросов, сервис недоступен или ошибка;
  - `session` — хранилище сессии: проверка `/me`, вход, выход, выход на всех устройствах, фоновая проверка после срока бездействия, но не реже раза в час, и при возврате на вкладку; прошедший или не сдвинувшийся срок проверяется снова через 30 с, проверка без ответа — через 60 с; адрес возврата после входа — только внутри `/app` или ровно `/invite/<UUID>`;
  - `organizations` — типы Auth (организация, членство, участник, приглашение, письмо, операция), порт `OrganizationsApi` и `collectPages`, который читает списки страницами до конца;
  - `organization-commands` — команды администратора через общий исполнитель: создание организации, добавление и удаление ресторана, удаление организации, часовой пояс, назначения и роль «Администратор», отзыв доступа, приглашения, повтор ссылки и отмена. Попытка с неизвестным исходом сохраняется вместе с введёнными значениями (`pendingOrganization`, `pendingRestaurantName`, `pendingMembership` и `checkMembership`, `pendingInvite`), «Проверить результат» повторяет её с тем же `commandID`; `clear()` снимает всё при выходе. Коды Auth превращаются в отказы экранов (`invalid`, `forbidden`, `conflict`, `last-admin`, `limited`, `gone` и другие);
  - `organization-reads` — модели чтения по организации: участники, приглашения и профиль (`GET /orgs/{orgID}`, только для администратора). Они читаются при открытии страницы, по «Обновить» и после своих команд, потому что живого потока для области Auth нет;
  - `lifecycles` — наблюдение за подготовкой ресторана и удалением ресторана или организации через `GET …/lifecycle/{operationID}`: состояния `following`, `finished`, `stalled` и `lost`; повтор подготовки заново запускает наблюдение;
  - `invitation-acceptance` — принятие приглашения на `/invite/:id`: форма имени и пароля для нового пользователя либо запрос кода для вошедшего, затем код из письма, регистрация или принятие и вход. Вызов кода и подтверждение переживают перезагрузку вкладки через порт `AcceptStorage`, пароль не сохраняется;
  - `credentials` — правила пароля (8–32 символа) и кода из шести цифр, общие для сброса пароля и приглашения; счёт идёт по кодовым точкам Unicode;
  - `switching` — решение о смене ресторана: перейти, спросить о неотправленной форме (W10) или остановиться на попытке с неизвестным исходом (W11); раздел без права у нового ресторана заменяется обзором (W12);
  - `live-feed` и `live-sync` — порт потока ресторана и сценарий реакции на его события, см. «Обновления в реальном времени»;
  - `read-model` — данные одного экрана; применяется только ответ на последний запрос;
  - `cookie-notice` и `feedback` — порты `CookieNoticeStore` и `FeedbackSender` и сценарий `createFeedbackSubmitter`. Сценарий сначала проверяет черновик. Для повторной отправки того же черновика он сохраняет `submissionID`, а после ответа `sent` создаёт новый.
- `adapters`:
  - `http/gateway-client` — обмен с gateway: `credentials: 'same-origin'`, `cache: 'no-store'`, CSRF-токен из `/me`, входа или `GET /api/v2/csrf` и одна повторная отправка после `InvalidCsrfToken`, заголовок `X-Umir-Runtime-Epoch` у команд warehouse и serving. Без ответа по контракту чтение получает исход `unavailable`, а изменение — `unknown`;
  - `http/read-request` — заголовок `X-Umir-Activity: background` для фоновых чтений;
  - `api/*` — `account-api`, `access-api`, `organizations-api` (организации, рестораны, участники, приглашения, профиль, операции) и `invitation-api` (запрос и проверка кода, регистрация и принятие по приглашению) поверх клиента, декодеры `decode/*` для отказов `#Error`, учётной записи, доступа, организаций, членств, приглашений, операций и контекста бизнес-чтения, сгенерированные типы `backend-v2.d.ts`;
  - `live/*` — `EventSource` на `GET /api/v2/r/{restaurantID}/live` и проверка `data` каждого события во время выполнения;
  - `browser-storage/last-restaurant-store` — последний открытый ресторан в `localStorage` под ключом `umir.lastRestaurant`; при недоступном storage ресторан не запоминается;
  - `browser-storage/cookie-notice-store` — закрытие cookie-уведомления в `localStorage` под ключом `umir.cookieNotice`; при недоступном storage состояние хранится в памяти;
  - `browser-storage/invitation-store` — вызов кода и подтверждение принятия приглашения в `sessionStorage` под ключом `umir.invite`; пароль не сохраняется, после перезагрузки его вводят снова. Разбор записи вызова общий со сбросом пароля (`challenge-record`);
  - `browser-page/*` — видимость вкладки через `visibilitychange` и таймеры `setTimeout`;
  - `feedback/*` — отправка обратной связи в `POST /api/v2/feedback/anonymous` (`feedback-api-sender`) и общий отправитель с путём, которым форма ресторана пользуется на `POST /api/v2/r/{restaurantID}/feedback` (`app-feedback-sender`).
- `presentation` — `theme`, общие компоненты `ui`, элементы сайта `site`, лендинг `landing`, документы `documents`, экраны входа, выхода и восстановления пароля `auth`, оболочка приложения и состояния доступа `app-shell`, экраны организации `organizations`, страницу приглашения `invite` и рабочие разделы `overview`, `orders`, `warehouse`, `catalog`. Экраны организации — список организаций и ресторанов, страница организации, создание предприятия, добавление и удаление ресторана, профиль и часовой пояс, участники и карточка участника с ролями и ролью «Администратор», отзыв доступа, приглашения со ссылкой и отменой, форма приглашения. Временных данных макета в `src` нет, кроме иллюстрации лендинга. Компоненты получают сценарии через `ServicesProvider`, а не создают адаптеры сами. Хуки из `session/hooks.ts` читают сессию, доступ, live-sync, попытки команд, «Данные обновились» и модели чтения через `useSyncExternalStore`.
- `app/main.tsx` — подключает шрифты, собирает клиент gateway, хранилища сессии и доступа, реестры эпох, моделей и команд, live-sync и адаптеры браузера с `crypto.randomUUID()`, `EventSource`, `fetch`, `localStorage`, таймерами и видимостью документа, затем монтирует провайдеры и маршрутизатор.

Бизнес-правила остаются на backend. Warehouse и serving определяют доступность, FEFO, истечение сроков и допустимый состав заказа. Frontend отображает ответы gateway и управляет только состоянием интерфейса. Он не дублирует решения сервисов.

При разработке экранов используйте React и библиотеки через публичные exports, а не внутренние пути пакетов. Не храните в state значения, которые можно вычислить из props или другого state, и не используйте `useEffect` для вычислений render. Запускайте независимые запросы параллельно. Выделяйте feature-модули, когда реальные экраны формируют устойчивые границы.

На лендинге и страницах документов показывается баннер о cookie, пока его не закроют. Фавиконки и `manifest.webmanifest` лежат в `public/`. Анимации hero сделаны на CSS keyframes. При `prefers-reduced-motion` элементы сразу показываются в конечном состоянии, а декор скрывается в режимах `forced-colors` и `prefers-contrast: more`.

Форма обратной связи проверяет поля на клиенте и отправляет сообщение в `POST /api/v2/feedback/anonymous` с версией согласия `2026-10-11`; повтор того же черновика использует тот же `submissionID`. Адрес офиса и часы поддержки — заполнители из макета; их нужно заполнить до публикации. Ссылки «Открыть приложение» ведут на вход. `GET /healthz` проверяет раздачу HTTP, а не готовность бизнес-функций.

На backend v2 подключены вход паролем, выход, сессия, доступ и оболочка `/app`, сброс пароля по почте с кодом, «Учётная запись» (имя и пароль) и форма лендинга. «Справочники», «Заказы», «Склад» и «Обзор» подключены к backend v2 (см. ниже). Что проверено вживую на стенде checkpoint (14.10), а что нет:

- профиль (`GET /api/v2/me`) и смена отображаемого имени — проверены;
- смена пароля — проверены сообщение L11 и вход новым паролем; состояние S16 («неверный текущий пароль») не воспроизведено: checkpoint отвечает `503 AuthUnavailable`, и страница показывает неизвестный исход;
- сброс пароля и форма лендинга — на момент проверки checkpoint не публиковал `email-challenges` (`404` простым текстом) и отвечал `403 InvalidCsrfToken` на форму лендинга, поэтому оба сценария проверены только тестами по контракту. Backend `main` (gateway `00f1e37`, serving `2e60b73`, auth `80561c4`; warehouse остаётся на checkpoint `9a87d84`) уже публикует маршруты сброса пароля и пропускает CSRF формы лендинга; живая проверка на нём ещё не повторялась.

Подключение устроено так:

- `/login` отправляет `POST /api/v2/session` с `commandID`. Если исход входа неизвестен, попытка сохраняется, а «Проверить результат» отправляет её с тем же `commandID`. Если сессию закончил сервер, страница входа сообщает «Сессия завершена».
- `/app` и все адреса под ним проверяют сессию через `GET /api/v2/me` до показа страницы. Гость попадает на `/login?return=…`. Если `/me` не ответил, показывается «Сессия не проверена» с повторной проверкой, а не вход.
- `/logout` вызывает `DELETE /api/v2/session`. После подтверждения выхода вкладка забывает попытки, эпохи, модели и доступ.
- Оболочка показывает отображаемое имя из `/me`, а рестораны, роли и права — из `GET /api/v2/access`. Раздел без права роли показывает «Раздел недоступен» (W14), отозванный ресторан — «Доступ к ресторану отозван» (W15), ещё не готовый — «Ресторан подготавливается» (W16). Адрес с неканоническим идентификатором ресторана показывает «Страницу не найдена».
- Меню учётной записи показывает рестораны организаций, в которых они есть, и переключает ресторан с сохранением раздела. При неотправленной форме сначала появляется вопрос (W10), попытка с неизвестным исходом останавливает переключение до проверки (W11), а раздел без права у нового ресторана заменяется обзором с пояснением (W12).
- Сообщения на странице входа L10, L11, L13 и L14 (пароль изменён, сессия закончена и другие) передаются через снимок сессии. Показанный на странице входа логин подставляется в поле.
- `/password-reset` ведёт сброс по почте через `POST /api/v2/email-challenges`, `POST /api/v2/challenges/{id}/verify`, `POST /api/v2/challenges/{id}/resend` и `POST /api/v2/email-challenges/{id}/complete`. Шаг сброса хранится в `sessionStorage` под ключом `umir.passwordReset` и переживает перезагрузку вкладки. Если исход шага неизвестен, проверка повторяет ту же команду с тем же `commandID`.
- `/app/settings` читает профиль из `GET /api/v2/me`, меняет имя через `PATCH /api/v2/me/display-name` и пароль через `PATCH /api/v2/me/password`. Несохранённое имя защищено диалогом ухода; пока исход изменения неизвестен, поля остаются закрытыми, в том числе после ухода со страницы и возвращения. Если сервер завершил сессию, пока исход смены пароля неизвестен, страница входа показывает L13 вместо «Сессия завершена», а попытка смены пароля снимается.
- Меню учётной записи и выдвижная навигация на 390 — нативный `<dialog>`: фокус остаётся внутри, Esc закрывает, фокус возвращается на кнопку.

Backend `main` публикует `GET /api/v2/access`. Если ответа нет (старый checkpoint отвечал `404`), `/app` показывает «Доступ не проверен» (W17), а адрес ресторана открывает оболочку со всеми разделами и подписью «Доступ не проверен» в блоке учётной записи: права проверяет gateway на каждом запросе.

«Справочники» и «Заказы» читают и пишут backend v2:

- «Справочники» — склад: продукты, каталог блюд, блюдо с рецептурой, подсказка кода, создание продукта и блюда (K01–K22);
- «Заказы» — serving: меню, стоп-лист, рекомендации, подготовка и оформление заказа со всеми исходами (кадры 01–08, B, C, D, E, F1, F2, F4, F5);
- количества приходят строками тысячных долей базовой единицы и не переводятся в `Number`: расчёты идут через `BigInt`, без потери точности;
- шапка разделов «Справочники» и «Заказы» показывает дату и зону организации;
- черновик заказа и незавершённая попытка оформления хранятся во вкладке (`sessionStorage`, ключ `umir.order.<userID>.<restaurantID>`). После перезагрузки «Проверить результат» повторяет ту же команду с тем же `commandID`; `resolve` доступен для «Оформление ожидает результата» и конфликта номера попытки. Если проверка отклонена gateway, неизвестная попытка сохраняется без новой команды. Выход и смена пользователя стирают записи;
- формы нового продукта и нового блюда сохраняют отправленные значения и ту же команду после ухода со страницы и возвращения;
- проверено тестами по контракту и 14.10 вживую в браузере на локальном стенде с backend `main`: справочники, создание продукта и блюда с конфликтом кода, полный заказ, потерянный ответ на оформление с перезагрузкой вкладки (проверка ушла с тем же `commandID`, продажа одна), двойное нажатие «Оформить». Предупреждение W11 при смене ресторана вживую не проверено: на стенде один ресторан.

«Склад» и «Обзор» читают и пишут backend v2:

- остатки — `GET …/warehouse/inventory`: колонки «Доступно», «Ожидает списания», «В наличии», «Истекает за 48 ч» и поиск по названию на клиенте. Партий и ближайшего срока в строках нет: `StockRow` их не содержит. Нулевой остаток и остаток, который целиком ожидает списания, — не ошибка;
- сроки годности: окно «24 ч» — партии из `expiring-batches`, которым осталось не больше 24 ч; окна «3 дня», «7 дней» и «Своя граница» — продукты из `analytics/stock` с `riskHours` и версией настроек организации из доступа (право `analytics.read`). Своя граница округляется вверх до целого часа, страница об этом предупреждает;
- подтверждение списания: блок «Ожидают списания» из `pending-writeoffs`, диалог и `POST …/warehouse/writeoffs`. Неизвестный исход проверяется через `GET …/warehouse/writeoffs/commands` с прежней эпохой склада; при `pending` и `unseen` повторяется та же команда. Попытка списания во вкладке не хранится: повторно списать партию нельзя (`AlreadyWrittenOff`);
- история читается от начала эпохи склада страницами по 500 до конца и показывается от новых к старым. События справочника скрыты; событие неизвестного типа останавливает показ всего журнала;
- приём поставки — `POST …/warehouse/deliveries`: время полей уходит местным временем зоны организации (`TimeInput.civil`), срок годности — в днях или месяцах. Повторяющийся час (DS01), несуществующий час (DS02) и смена зоны организации (DS03) показываются у формы. Черновик, `deliveryID` и незавершённая попытка хранятся во вкладке (`sessionStorage`, ключ `umir.delivery.<userID>.<restaurantID>`). После перезагрузки «Проверить результат» повторяет ту же команду с тем же `commandID` и `deliveryID`, второго прихода нет. Выход и смена пользователя стирают записи, истечение сессии — нет;
- «Обзор» показывает плитки по правам роли в ресторане: «Официанту» — «Меню и рекомендации» и «Заказы» с кнопкой «Собрать заказ», роли «Склад» — склад, меню, справочники, под списание и аналитику без «Собрать заказ». Каждая плитка читает, загружается и ошибается отдельно; незавершённая попытка оформления видна на плитке «Заказы»;
- шапка «Склада» и «Обзора» показывает дату и зону организации, а строку «{организация} · {ресторан}» «Обзор» берёт из доступа;
- проверено тестами по контракту и 2026-10-14 вживую в браузере на локальном стенде с backend `main`: поставка с просроченной строкой, остатки, окна сроков, подтверждение списания, история, потерянный ответ на поставку с перезагрузкой вкладки (проверка ушла с тем же `commandID` и `deliveryID`, поставка одна), двойное нажатие «Принять поставку» и «Списать партию», «Обзор» администратора. Не проверено вживую: роль «Официант» (на стенде только администратор, роль покрыта тестом), смена часа и пояса организации, смена настроек и сброс среды, более 500 продуктов и событий, живые обновления (`/live` отвечает 403).

Разделы «Меню и рекомендации» (`/menu`) и «Аналитика» (`/analytics`) — пустые страницы с заголовком: макета нет. Поиск в меню учётной записи фильтрует рестораны.

Экраны организации работают на backend v2 (контракт UA1, область Auth). Организации, рестораны и роли берутся из `GET /api/v2/access` (администратор видит и готовящиеся рестораны), а списки участников и приглашений и профиль организации читаются отдельно по `/api/v2/orgs/{orgID}/…`. Команды идут через общий исполнитель с одним `commandID` на попытку: если ответ потерян, экран пишет «Результат … неизвестен», а «Проверить результат» повторяет ту же попытку с теми же значениями. Неизвестный идентификатор организации в адресе показывает «Страницу не найдена».

- Готовность ресторана (`registering`) и удаление наблюдаются через `GET …/lifecycle/{operationID}`; «Повторить подготовку» заново запускает наблюдение, а подготовку повторяет сам Auth.
- Приглашение уходит только в готовые рестораны (`ready`); готовящийся показан недоступным. Почта, которая уже в списке участников, отклоняется на клиенте (Auth такую почту не отклоняет, а принятие упало бы с `CommandConflict`).
- Устаревшая версия назначений или настроек (`CommandConflict`, `SettingsChanged`) перечитывает данные и не отправляет черновик повторно сам. `LastAdmin` показывается отказом, строка текущего пользователя в списке участников не открывается.
- Часовой пояс выбирается из статического списка IANA (`ui/zones.ts`), смещение считает `Intl` на текущий момент. Время и даты в списках показываются в зоне организации.
- Принятие приглашения `/invite/:invitationID` для нового пользователя начинается с имени и пароля, для вошедшего — сразу с запроса кода. Код привязан к сеансу, в котором его запросили, поэтому смена режима посреди сценария начинает его заново. Пароль не сохраняется в `sessionStorage`.
- «Выйти на всех устройствах» (`/app/settings`, «Сеансы») отзывает все сессии; неизвестный исход проверяется `GET /me`: `401` означает, что выход выполнен.
- Обратная связь из приложения открывается по `/app/r/:restaurantID/feedback` и использует правила формы лендинга.
- Настройка автосписания организации появится вместе с контрактом UA2.

API-клиент обращается к backend только через gateway. Типы генерируются из закреплённого контракта (см. [«Контракт API»](#контракт-api)), но не заменяют проверку JSON во время выполнения: каждый ответ проверяют декодеры из `adapters/api/decode`. Декодер обязан разбирать все известные варианты `kind/type`; неизвестный или некорректный ответ команды не является успехом или доказательством отсутствия записи.

`openapi-typescript` установлен и генерирует API-типы. Playwright разрешён для браузерной приёмки, но в проект не установлен: ручная приёмка запускает его из отдельной рабочей папки. Unit-тесты используют Bun.

Целые количества из wire-контракта передаются строками. Не преобразуйте их в `Number`; сохраняйте строку или используйте `BigInt`. Даты должны сохранять полный timestamp и часовой пояс `Europe/Moscow`. Неизвестный результат подтверждения и `ConfirmationPending` сохраняют ту же попытку и `commandID`; их нельзя показывать как успех или повторять с новым идентификатором.

Браузерные сценарии проходят через frontend/Nginx → gateway → реальные serving/warehouse. Межмодульные tests/business и HTTP-проверки tests/http фабрики подтверждают свои уровни поведения; отдельная браузерная приёмка требуется после реализации UI. Проверки интерфейса должны охватывать все варианты результата, клавиатурную навигацию и ширины 1440, 1024 и 390. Проверяйте длинные русские названия, точные большие количества, причины недоступности, фокус, ошибки, ожидание и подтверждённый результат. Сборка и статическая проверка архитектуры не доказывают корректность бизнес-семантики или runtime-JSON.

Публичные поля и варианты ответов описаны в закреплённом контракте `api/ui-amendment-v1-composed-public.json`, а бизнес-правила — в [спецификации business-core](https://github.com/JustIkra/umir-factory/blob/main/docs/business-core.md). Фабрика выбирает опубликованные образы по точным SHA; новая версия исходников не меняет выбранную сборку автоматически. Сверяйте контракт и образы с выбранными SHA фабрики.

### Обновления в реальном времени

Gateway сообщает об изменениях ресторана потоком SSE `GET /api/v2/r/{restaurantID}/live`. Поток передаёт только сигналы, а данные экраны перечитывают обычными GET.

Адаптер `live/event-source-feed.ts` разбирает `data` событий `change`, `refresh-required` и `access-ended` по контракту. `tenantID` и `epoch` — канонические UUID, `sequence` — положительное int64 и хранится как `BigInt`, `topics` — от одной до пяти неповторяющихся тем из `catalog`, `stock`, `menu`, `orders`, `analytics`. Некорректное событие закрывает `EventSource`, и адаптер сообщает `closed`. После разрыва соединения браузер переподключается сам и передаёт `Last-Event-ID`. После ответа, отличного от `200 text/event-stream` (`401`, `403`, `429` или `502` от Nginx), браузер закрывает поток, и адаптер тоже сообщает `closed`. Следующая подписка один раз продолжает с последнего `id` через `?cursor=`, а курсор, отклонённый до открытия потока, забывается.

Сценарий `createLiveSync` из `application/live-sync.ts`:

- `change` с тем же `epoch` и большим `sequence` помечает устаревшими модели ресторана с темами события. Номер не больше известного ничего не меняет. Новый `epoch` перечитывает всё.
- `refresh-required` перечитывает все модели ресторана и начинает отсчёт номеров заново в указанном `epoch`.
- `access-ended` с причиной `session-expired` заканчивает сессию, и приложение переходит на вход с «Сессия завершена». Причины `revoked` и `deleted` останавливают поток и перечитывают доступ. `auth-unavailable` временна: поток закрывается и после проверки сессии подключается снова.
- Попытки `ConfirmationPending` проверяются через `resolvePending` после каждого нового `change`, после `refresh-required` и после первого `change` нового подключения, по одному вызову за раз. Сигналы во время вызова дают ровно один следующий вызов. Пока `resolvePending` ничего не проверяет: экранов с такими попытками ещё нет.
- В v2 нет события `tick`: модели, зависящие от времени (окно сроков, рекомендации), перечитываются раз в минуту. Относительные метки только форматируют серверный `expiresAt`; истечение определяет сервер.
- Если поток не открыт 10 с, флаг `stale` в состоянии сценария сообщает, что показанные данные могли устареть. Повторные попытки подключения не начинают отсчёт 10 с заново.
- Если адаптер сообщил `closed`, сценарий проверяет сессию через порт `SessionCheck`: браузер не сообщает, отказал ли gateway с `401` или Nginx с `502`. Закончившаяся сессия останавливает поток навсегда. В остальных случаях, в том числе когда проверка не получила ответа, поток подключается снова: первый раз через 3 с, как `retry: 3000` потока, затем через 6, 12, 24 и 48 с и дальше через каждые 60 с; открытый поток возвращает задержку к 3 с. Если сессия жива, после отказа приложение в фоне перечитывает доступ: закончившийся доступ показывает W15 и останавливает поток. Отсчёт 10 с при этом не сбрасывается, а `stop()` отменяет ожидаемую проверку и переподключение.
- Скрытая вкладка откладывает перечитывание до `visibilitychange` и затем перечитывает один раз.

Модель чтения `createReadModel` из `application/read-model.ts` хранит ответ одного экрана. Порядок ответов задаёт счётчик запросов клиента, а не `stateVersion`: ответ на более ранний запрос отбрасывается. Модель без подписчиков только запоминает, что устарела, и читает при следующей подписке. Если запрос уже идёт, а модель снова помечена устаревшей, после него выполняется ровно один запрос. Загрузчик получает `{ background }`: `true` при перечитывании по сигналу или по минутному такту. Неудачное чтение сохраняет прежние данные, время последнего успешного чтения `loadedAt` и причину отказа.

Перечитывание по сигналу или такту отправляет `X-Umir-Activity: background`: gateway проверяет сессию, но не продлевает её. Смысл имеет только точное значение `background`. Запросы, вызванные оператором, идут без заголовка и продлевают сессию. Тот же заголовок несёт фоновая проверка сессии: `200` от `GET /api/v2/me` означает, что сессия жива, `401` — что она закончилась, а любой другой ответ или его отсутствие оставляют состояние неизвестным.

Live-sync передаётся экранам через `ServicesProvider` незапущенным, поэтому публичные страницы поток не открывают. Оболочка ресторана `/app/r/:restaurantID` вызывает `live.start(restaurantID)`, а уход из неё и выход — `live.stop()`. Модели чтения регистрируются в `ModelRegistry` с рестораном и темами потока; экраны разделов их пока не используют.

## Разработка

Для npm-команд нужен Node.js 22.13+, 24.x или 26+. CI и Docker-сборка закреплены на Node.js 24.21.0. Bun 1.4.3 закреплён в `.bun-version`; тестовый preload проверяет, что запущена именно эта версия. Установите её по [инструкции Bun](https://bun.com/docs/installation#installing-a-specific-version). npm остаётся менеджером установки и использует `package-lock.json`.

```sh
npm ci
npm run dev
```

Откройте приложение по адресу `http://127.0.0.1:5173`, а не `localhost`: в режиме loopback gateway принимает только `Origin` с IP-адресом. Dev-сервер Vite передаёт `/api` в gateway по адресу из `UMIR_GATEWAY_URL` (по умолчанию `http://127.0.0.1:18081`).

Локальный backend v2 собирают и запускают скрипты из рабочей папки `umir-2026/dev/backend-v2`. Она лежит вне этого репозитория, рядом с ним в рабочем каталоге umir-2026; порядок запуска описан в её `README.md`.

Backend `main` (gateway `00f1e37`, serving `2e60b73`, auth `80561c4`; warehouse остаётся на checkpoint `9a87d84`) публикует `/api/v2/access` и маршруты сброса пароля и пропускает CSRF формы лендинга; на локальном стенде ресторан становится готовым, а чтения склада и serving через gateway отвечают `200`. Режимы запуска описаны в `umir-2026/dev/backend-v2/README.md` (вне репозитория).

Известные дефекты backend:

- `GET /api/v2/r/{restaurantID}/live` всегда отвечает `403 Forbidden`: gateway проверяет доступ через Auth с операцией `live`, а Auth такой операции не знает. Живых обновлений нет: изменения из других вкладок и устройств видны только после повторного чтения.
- `GET /api/v2/csrf` с cookie сессии, которую сервер уже завершил, отвечает `401 Unauthenticated`, не выдаёт preauth и оставляет cookie. Вход при этом заблокирован, пока пользователь не удалит cookie `umir_operator_session`.

### Прокси API

Браузер обращается к API только через этот Nginx (gateway#8, gateway#10). Для `/api/`:

- `Host` браузера вместе с портом, `Origin`, cookie и `X-CSRF-Token` доходят до gateway без изменений, как и исходные путь и query. Статус, тело и `Set-Cookie` ответа gateway возвращаются без изменений, в том числе его ошибки.
- Ответы не кешируются, запрос не повторяется. Таймаут или разрыв после передачи — неизвестный исход, его разрешает клиент.
- Таймауты: соединение 5 с, отправка и чтение 30 с. Gateway ограничивает обмен `UPSTREAM_TIMEOUT` (15 с) и чтение тела запросов кабинета (10 с); если поднять `UPSTREAM_TIMEOUT`, `proxy_read_timeout` должен остаться больше.
- Собственные ошибки Nginx — JSON в форме `#Error` контракта вместо HTML-страниц, всё с `Cache-Control: no-store`: `502 UpstreamUnavailable` и `504 UpstreamTimeout` с `retryable: true` и `outcome` (`unavailable` для `GET`, `HEAD`, `OPTIONS`, иначе `unknown`), `413 PayloadTooLarge` с `outcome: not_committed`, `retryable: false` и `requestID`.
- Обе формы обратной связи — публичная `POST /api/v2/feedback/anonymous` и форма ресторана `POST /api/v2/r/{restaurantID}/feedback` — принимают тело до 16 КиБ, остальные маршруты — до 1 МиБ, как по умолчанию в Nginx.
- Поток SSE `GET /api/v2/r/{restaurantID}/live` идёт через отдельный `location ~ ^/api/v2/r/[0-9a-f-]+/live$`: HTTP/1.1 с пустым `Connection`, без буферизации, кеша и gzip, таймаут чтения 60 с. Gateway шлёт `: ping` каждые 15 с, поэтому тихий поток не обрывается. Собственный `proxy_set_header` отменяет наследование серверных заголовков, поэтому `Host`, `X-Forwarded-For` и `X-Forwarded-Proto` в этом блоке повторены. Собственные ошибки Nginx `502` и `504` — тот же `#Error` с `outcome: unavailable`.

- Страница приглашения `location /invite/` отдаёт `index.html` через `rewrite ^ /index.html break` (а не `try_files`, который перешёл бы в другой `location`) и добавляет `Referrer-Policy: no-referrer`: ссылка приглашения не должна попадать в `Referer`.

`npm run test:nginx` запускает `nginx.conf` в закреплённом образе Nginx из `Dockerfile` вместе с заглушкой gateway на Node.js из того же файла и проверяет эти правила; нужны Docker с Compose и Node.js. Ответ `504` по таймауту и 60-секундный таймаут потока автоматически не проверяются: это заняло бы 30 и 60 секунд. Nginx 1.30 и без отдельного блока ходит в gateway по HTTP/1.1 и сразу передаёт события, поэтому проверка дополнительно сверяет блок потока в `nginx.conf` с контрактом.

### Контракт API

Каталог `api/` хранит побайтовые копии composed-контракта UA1 из `umir-factory@9d4941cffcea42608b203ed0a1d00ea0226c32cf` (`info.version` = `2.0.0-UA1.1`): `ui-amendment-v1-composed-public.json`, `backend-v2-examples.json` и `ui-amendment-v1-examples.json`. Их SHA-256 закреплены в [api/README.md](api/README.md); файлы не правят и не форматируют вручную.

- `npm run api:types` генерирует из `ui-amendment-v1-composed-public.json` типы `src/adapters/api/backend-v2.d.ts` через `openapi-typescript` и форматирует их Prettier.
- `npm run api:check` входит в `npm run check`: сверяет SHA-256 трёх файлов с закреплёнными и проверяет, что `backend-v2.d.ts` совпадает с новой генерацией.

Сгенерированные типы используют только адаптеры. Они описывают тела запросов, а ответы проверяют декодеры во время выполнения. Чтобы обновить контракт, скопируйте новые файлы, обновите таблицу в `api/README.md` и выполните `npm run api:types`.

## CI/CD и версии

[GitHub Actions](https://github.com/JustIkra/umir-frontend/actions) проверяет push в ветки, pull request в main и ручные запуски. После успешных проверок main публикует `ghcr.io/justikra/umir-frontend:sha-<полный SHA коммита>` для `linux/amd64` и `linux/arm64`. Задание публикации получает `packages:write`; остальные задания имеют только `contents:read`.

Фабрика закрепляет выбранный SHA в `compose.yaml`. Обновление фабрики выполняется отдельным PR; новый образ не развёртывается автоматически.

Используйте Conventional Commits и Semantic Versioning. До 1.0 совместимые исправления увеличивают patch, а новые возможности или несовместимые изменения — minor. Записывайте миграцию для несовместимых изменений. Репозитории и релизы ведутся отдельно. Для выпусков применяйте аннотированные `vX.Y.Z` теги; опубликованные версии и теги неизменны. Сохраняйте идентификаторы образов `sha-<полный SHA>` и точные pins фабрики.
